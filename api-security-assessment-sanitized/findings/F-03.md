# F-03 — XSS Armazenado (Candidato) via Campo `name` do Perfil

- **Severidade:** MEDIUM
- **CVSS v3.1:** 5.4 (AV:N/AC:L/PR:L/UI:R/S:U/C:L/I:L/A:N)
- **CWE:** CWE-79 (Cross-site Scripting) — CWE-80 (Neutralização Impropria de Tags HTML Relacionadas a Script)
- **OWASP 2021:** A03 — Injection
- **MITRE ATT&CK:** T1059.007 — Command and Scripting Interpreter: JavaScript

---

## Descrição

O endpoint `PATCH /user/profile` aceita payloads arbitrários de HTML/script no campo `name`
e os persiste sem sanitização no servidor. Payloads como `<svg onload=alert(1)>`,
`<script>alert(document.cookie)</script>` e template-strings (`{{7*7}}`, `${7*7}`,
`<%= 7*7 %>`) são armazenados e depois retornados por `GET /user/{id}`.

As respostas da API são JSON com escaping adequado (`\u003cscript\u003e`), então o payload
**não** executa em uma resposta de API somente-JSON. O risco se materializa se qualquer
front-end consumidor renderizar esse campo via `innerHTML`/`v-html` sem escaping — um padrão
comum em dashboards admin e visualizações de loja. Os payloads de template-string retornados
como literais confirmaram que **SSTI não está presente** (Go não faz template de nomes
controlados pelo usuário).

## Impacto

- Se qualquer front-end (admin/loja/customer) renderizar o campo `name` sem sanitização, um
  atacante pode executar script na sessão de outro usuário (roubo de sessão, takeover de
  conta, ações de admin).
- Mesmo sem um consumidor explorável hoje, armazenar HTML controlado por atacante é um
  stored-XSS latente esperando qualquer nova UI que o renderize.

## Evidência (sanitizada)

```http
PATCH /user/profile HTTP/1.1
Authorization: Bearer <customer_jwt>
Content-Type: application/json

{"name":"<script>alert(document.cookie)</script>"}
```

```http
HTTP/1.1 200 OK
```

```http
GET /user/{id} HTTP/1.1
Authorization: Bearer <customer_jwt>
```

```json
{
  "id": "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx",
  "name": "\u003cscript\u003ealert(document.cookie)\u003c/script\u003e",
  "role": "customer"
}
```

## Remediação

1. Sanitizar no servidor antes da persistência (`html.EscapeString` ou allow-list estrita
   de caracteres para o nome), ou rejeitar markup com `400 invalid name`.
2. Aplicar CSP forte em todos os front-ends (`script-src 'self'`) e usar auto-escaping
   ciente de contexto (sem `innerHTML` para dados de usuário).
3. Adicionar um teste unitário afirmando que `name` não pode conter `<`/`>`; estender a
   suíte com teste de render DOM no repositório do front-end.
