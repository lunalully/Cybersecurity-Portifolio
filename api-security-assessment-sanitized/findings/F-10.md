# F-10 — Catálogo Ignora JWT Inválido (Mascara Bugs de Auth no Cliente)

- **Severidade:** LOW
- **CVSS v3.1:** 2.6 (AV:N/AC:H/PR:N/UI:N/S:U/C:L/I:N/A:N)
- **CWE:** CWE-287 (Autenticação Impropria) — comportamental/informacional
- **OWASP 2021:** A07 — Identification and Authentication Failures
- **MITRE ATT&CK:** T1078 — Valid Accounts

---

## Descrição

Os endpoints de catálogo tratam o JWT como **opcional**: um token válido injeta a identidade
do usuário, um token **inválido** é ignorado e a requisição prossegue como anônima (`200`).
Confirmado em 7 endpoints de catálogo (`/cuisines`, `/stores`, `/store/{id}/menus`, …) com
três variações: sem token → 200, `Bearer invalid123` → 200, `Bearer <valid_customer>` → 200.

Isso é intencional para um catálogo público, mas a degradação silenciosa significa que um bug
de front-end que envia um token malformado recebe `200` com dados **anônimos** —
possivelmente perdendo campos com escopo de usuário (ex. `is_favorite`) sem nenhum erro,
tornando bugs de auth do cliente invisíveis.

## Evidência (sanitizada)

```bash
curl -sk https://api.example.com/cuisines -H "Authorization: Bearer invalid123"
# HTTP 200  (igual ao anônimo — token inválido silenciosamente ignorado)
```

## Remediação

1. Manter o `200` do catálogo público, mas logar `invalid_token` em nível WARN para que
   regressões de auth no cliente sejam detectáveis.
2. Onde uma rota retornar dados com escopo de usuário (favoritos, preferências), exigir token
   válido ou expor explicitamente `401` para que fallbacks anônimos nunca sejam silenciosos.
