# F-09 — Criação de Pedido Idempotente Silenciosa (Sem Idempotency-Key)

- **Severidade:** LOW
- **CVSS v3.1:** 3.1 (AV:N/AC:L/PR:L/UI:N/S:U/C:N/I:L/A:N)
- **CWE:** CWE-799 (Controle Improprio da Frequência de Interação) / CWE-770
- **OWASP 2021:** A04 — Insecure Design
- **MITRE ATT&CK:** T1498 — Network Denial of Service (reuso de recurso)

---

## Descrição

`POST /store/{id}/order` é silenciosamente idempotente: duas chamadas consecutivas com o
mesmo `menu_id` retornam o **mesmo ID de pedido** em status `CREATED` com array `items`
vazio, em vez de criar um novo carrinho. Embora isso evite pedidos duplicados (um positivo),
o comportamento é implícito e não documentado. Um cliente que espera um carrinho novo a cada
chamada silenciosamente reusa o pedido vazio anterior. O invariante "um único pedido
`CREATED` ativo por loja/usuário" é aplicado sem contrato explícito, sem header
`Idempotency-Key` e sem `409`.

## Impacto

- Confusão do cliente: retries podem mutar um carrinho anterior não relacionado em vez de
  começar do zero.
- Acoplamento oculto de lógica de negócio — se o invariante mudar, bugs de pedido duplicado
  podem aparecer silenciosamente.

## Evidência (sanitizada)

```bash
# Duas chamadas sequenciais, mesmo menu_id
curl -sk -X POST https://api.example.com/store/xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx/order \
  -H "Authorization: Bearer <customer_jwt>" -H "Content-Type: application/json" \
  -d '{"menu_id":"xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"}'
# chamada 1 → id: d339f…-…-… (CREATED, items:[])
# chamada 2 → id: d339f…-…-… (mesmo ID, CREATED, items:[])
```

## Remediação

1. Documentar o contrato explicitamente: "no máximo um pedido `CREATED` por loja/usuário".
2. Preferir `Idempotency-Key` explícita fornecida pelo cliente (retornar `409` em conflito, ou
   reusar o pedido existente com um header claro), ou retornar `409` quando o cliente indicar
   que espera um novo recurso.
