# F-11 — Rate Limit Depende de Redis — Sem Fallback

- **Severidade:** LOW
- **CVSS v3.1:** 3.7 (AV:N/AC:H/PR:N/UI:N/S:C/C:L/I:N/A:N)
- **CWE:** CWE-636 (Não Falhar Fechado Quando Ocorre Erro) / CWE-400
- **OWASP 2021:** A07 — Identification and Authentication Failures
- **MITRE ATT&CK:** T1498 — Network Denial of Service

---

## Descrição

Todo o rate limiting é backed by Redis. Quando o Redis está indisponível, o limiter é
ignorado e toda rota — incluindo autenticação — fica ilimitada. A arquitetura não tem
fallback em memória. Isso foi confirmado como comportamento a nível de código a partir do
inventário: "rate limit só existe com Redis; sem Redis, as rotas não têm limite".

## Impacto

- Se o Redis degradar durante um ataque, o rate limit de auth desaparece exatamente quando é
  mais necessário — habilitando bursts de credential stuffing e brute force de login.
- Uma única dependência de infraestrutura é um ponto único de falha para um controle central.

## Evidência (sanitizada)

Observação a nível de código do inventário (paráfrase):

```go
// limiter.NewRedisLimiter(...) — se o cliente Redis der erro, as requisições passam
```

## Remediação

1. Adicionar limiter de fallback em memória (ex. `golang.org/x/time/rate`) para auth/catálogo/
   webhook quando o Redis estiver fora — fail-closed, nunca fail-open.
2. Testar o comportamento com o Redis intencionalmente parado em staging.
3. Considerar rate limit por IP na borda (CDN) como defense-in-depth (ver F-14).
