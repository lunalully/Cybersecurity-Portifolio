# F-01 — Escalada Vertical de Privilégio via Auto-Registro de Loja

- **Severidade:** HIGH
- **CVSS v3.1:** 8.8 (AV:N/AC:L/PR:L/UI:N/S:C/C:H/I:H/A:N)
- **CWE:** CWE-269 (Gerenciamento Improprio de Privilegios) / CWE-284 (Controle de Acesso Improprio)
- **OWASP 2021:** A01 — Broken Access Control · A04 — Insecure Design
- **MITRE ATT&CK:** T1078 — Valid Accounts

---

## Descrição

Uma conta `customer` comum pode escalar para privilégios de `store_owner` simplesmente
chamando `POST /store`. O endpoint **não faz nenhuma checagem de role** — qualquer usuário
autenticado pode criar uma loja e se tornar o dono dela. O fluxo de criação de loja apenas
valida o formato do CNPJ e os campos obrigatórios (retornando `400 invalid_argument` em
entrada inválida), nunca verificando se quem requisita tem permissão para ter a role
`store_owner`.

Uma vez criada a loja, a conta escalada ganha acesso a todas as capacidades de
`store_owner` **na própria loja**: gestão de menu, gestão de pedidos, métricas, configuração
de pagamento e gestão de cupons. O isolamento horizontal (possuir *outras* lojas) permanece
correto — um `store_owner` não toca a loja de outro dono — mas a fronteira vertical
`customer → store_owner` não é aplicada.

## Impacto

- Qualquer customer autenticado pode virar lojista sem aprovação ou verificação.
- Habilita criação em massa de vitrines falsas (combina com F-02).
- Se o modelo de negócio exige onboarding aprovado, isso é um bypass direto da política de
  onboarding e abre porta para abuso da plataforma, fraude e dano de reputação.

## Evidência (sanitizada)

```http
POST /store HTTP/1.1
Host: api.example.com
Authorization: Bearer <customer_jwt>
Content-Type: application/json

{"name":"Store Invader","slug":"store-invader","cnpj":"00.000.000/0001-91"}
```

```http
HTTP/1.1 200 OK

{"id":"xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx","name":"Store Invader", ...}
```

Follow-up:

```http
GET /user/stores
Authorization: Bearer <customer_jwt>
```

```json
[{"id":"xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx","name":"Store Invader"}]
```

A mesma conta então chamou com sucesso `POST /store/{id}/menu` (200) e
`GET /store/{id}/metrics` (200) — capacidades completas de `store_owner`.

## Remediação

1. Aplicar um gate de role no `POST /store` — retornar `403 insufficient permissions` quando
   o requisitante não for `store_owner` (ou adicionar um fluxo explícito de aprovação de
   onboarding de `store_owner`).
2. Se o onboarding self-service for intencional, documentá-lo e adicionar controles
   anti-abuso: fila de aprovação, verificação de CNPJ e rate limiting (ver F-06).
3. Adicionar um teste de integração afirmando `customer → POST /store → 403`.
